# WhiteNoise Key Management Overview

## 1. Introduction

WhiteNoise is an MLS-based encrypted group messenger built on Nostr.
Key management spans two cryptographic domains:

- **Nostr identity** (secp256k1) -- Schnorr signing for relay
  authentication, event publishing, NIP-44 encrypted DMs, and
  AccountIdentityProof binding.
- **MLS group encryption** (Ed25519 + X25519) -- Ed25519 signing for
  MLS commits, proposals, and application messages; X25519 HPKE key
  agreement for KeyPackage init keys, Welcome decryption, and
  UpdatePath decryption.

WhiteNoise supports three key management modes: classical (random keys
on disk), HD shared (deterministic from mnemonic, same MLS identity on
all devices), and HD device-bound (deterministic, per-device MLS
identity). The mode determines recovery properties, multi-device
behaviour, and the operational tradeoffs around MLS epoch coordination.

---

## 2. Architecture -- KeyMaster to Avatar to WhiteNoise

The target architecture separates key material from the application
through a three-layer connection chain. WhiteNoise never holds private
keys in-process.

### Full KeyMaster path (via relay)

```
┌──────────────────┐
│  KeyMaster       │  Vault process -- holds mnemonic, derives all keys.
│  (remote vault)  │  Runs on a trusted device (phone, hardware token).
└────────┬─────────┘
         │  NIP-44 encrypted events (kind 27235) over Nostr relay
         │
┌────────┴─────────┐
│  km-nostr-sa     │  Local avatar proxy -- translates between
│  (avatar)        │  Unix-socket JSON-RPC and NIP-44 relay transport.
└────────┬─────────┘
         │  Unix socket, JSON-RPC 2.0, 4-byte BE length-framed
         │  env: NOSTR_SA_SOCK=<path>
         │
┌────────┴─────────┐
│  WhiteNoise      │  Application -- no key material in process.
│  (no secrets)    │  Delegates all signing and key agreement.
└──────────────────┘
```

### sa-daemon shortcut path (local vault, no relay hop)

For development and single-machine deployments, the `sa-daemon`
replaces both KeyMaster and the avatar. It holds the mnemonic
directly and serves the same 11 JSON-RPC methods over the same Unix
socket interface. WhiteNoise cannot distinguish the two -- the
protocol is identical.

```
┌──────────────────┐
│  sa-daemon       │  Local vault daemon -- holds mnemonic + vault.
│  (KmLight)       │  Binds $XDG_RUNTIME_DIR/nostr-sa-light.<pid>.sock
└────────┬─────────┘
         │  Unix socket, JSON-RPC 2.0, 4-byte BE length-framed
         │  env: NOSTR_SA_SOCK=<path>
         │
┌────────┴─────────┐
│  WhiteNoise      │  Same binary, same boot sequence.
│  (no secrets)    │  Identical code path for both backends.
└──────────────────┘
```

### Wire protocol

| Property       | Value                                       |
|----------------|---------------------------------------------|
| Transport      | Unix domain socket                          |
| Framing        | 4-byte big-endian length prefix + JSON body |
| Encoding       | JSON-RPC 2.0                                |
| Byte arrays    | Hex-encoded strings (Nostr convention)      |
| Max frame      | 1 MiB                                       |

Startup: the daemon (or avatar) binds the socket and prints
`NOSTR_SA_SOCK=<path>; export NOSTR_SA_SOCK;` on stdout. WhiteNoise
reads the variable from the environment and connects.

## 3. Classical Mode (Standalone, Keys on Disk)

This is the original WhiteNoise design before KeyVault integration.

- **Nostr identity**: a random nsec (secp256k1 scalar), imported by
  the user or generated at account creation.
- **Nostr key storage**: password-encrypted `vault.db` on Linux
  desktop (Argon2id KDF + XChaCha20Poly1305), or platform keyring
  (macOS Keychain, Linux keyutils, Android keystore) via
  `keyring-core`.
- **MLS signing key**: random Ed25519 keypair generated per device by
  `RustCrypto` inside OpenMLS. Private key stored in a SQLCipher
  database (`$DATA_DIR/mls/<pubkey>/db.sqlite`).
- **HPKE init keys**: random X25519 keypairs, one per KeyPackage,
  generated by `RustCrypto`. Private keys stored in the same SQLCipher
  database.
- **AccountIdentityProof**: BIP-340 Schnorr signature binding the
  Nostr npub to the MLS Ed25519 public key. Both keys are independent
  random values.
- **Recovery**: requires backup of the vault (or keyring export) *and*
  the SQLCipher database *and* the vault password. Loss of any
  component means loss of the MLS identity or the Nostr identity.
- **Multi-device**: each device has independent random keys. No
  relationship between devices beyond sharing the same Nostr npub (if
  the nsec was copied manually).

## 4. HD Mode -- Shared (No Device ID)

All keys are derived deterministically from a single BIP-39 mnemonic.
All devices sharing the mnemonic derive the **same** Nostr identity
and the **same** MLS identity.

- **Seed**: BIP-39 mnemonic (12 or 24 words) fed through BIP-32
  hierarchical derivation.
- **Nostr identity**: derived at
  `m/44'/1237'/mangle(email)'/SCHNORR|0|0'/0|0'` (secp256k1).
- **MLS signing key**: derived at
  `m/44'/1242'/mangle(email)'/ED25519|0|SIGN'/0|0'` (Ed25519).
- **HPKE init keys**: derived at
  `m/44'/1242'/mangle(email)'/ED25519|0|HPKE'/0|N'` (X25519),
  where N is a monotonically increasing index.
- **Identity string**: `mangle(email)` produces a 31-bit hash via
  SHA-256 truncation, used as the BIP-32 identity level.
- **Recovery**: mnemonic only. All keys are re-derivable. No vault
  backup, no database export, no password.
- **Multi-device**: every device with the mnemonic derives the same
  MLS leaf. Only one device should commit to a group at a time.

### Tradeoffs

- **Epoch conflicts**: two devices sharing the same MLS leaf cannot
  independently advance the epoch. A commit from device A invalidates
  device B's pending state. Coordination happens naturally through
  relay observation -- devices that see each other's messages stay
  synchronized.
- **Sender ratchet**: MLS maintains a per-leaf sender ratchet. If two
  devices send messages concurrently on the same group, the ratchet
  state diverges and recipients may fail to decrypt. In practice this
  requires near-simultaneous sends on the same group.
- **HPKE index coordination**: the init key counter must not collide
  between devices. Devices coordinate via the relay -- published
  KeyPackages (kind-30443 events) contain the HPKE init public key.
  A recovering device scans derivation indices against published
  KeyPackages to find the next unused index.

---

## 5. HD Mode -- Device-Bound (With Device ID)

Each device derives a **different** MLS identity by mixing a hardware
identifier into the mangle input. The Nostr identity remains shared.

- **Identity string**: `mangle(email + ":" + deviceId)` produces a
  device-specific 31-bit hash.
- **Nostr identity**: `mangle(email)` -- same across all devices
  (Nostr branch does not include deviceId).
- **MLS signing key**: derived at
  `m/44'/1242'/mangle(email:deviceId)'/ED25519|0|SIGN'/0|0'` --
  unique per device.
- **HPKE init keys**: derived at
  `m/44'/1242'/mangle(email:deviceId)'/ED25519|0|HPKE'/0|N'` --
  unique per device.
- **Recovery**: mnemonic + knowledge of device IDs. The mnemonic
  alone is not sufficient to reconstruct a specific device's MLS
  identity without its device ID.

### Tradeoffs

- **Independent MLS leaves**: each device is a separate group member.
  Standard MLS multi-device model ("Alice's laptop" and "Alice's
  phone" are distinct leaves).
- **Concurrent commits**: both devices can commit independently
  without epoch conflicts -- they hold different positions in the
  ratchet tree.
- **Device loss**: losing a device means that device's leaf must be
  removed from all groups. The keys can be re-derived if the device
  ID is known.
- **Device ID stability**: the hardware identifier (e.g. CPU serial,
  machine-id) must survive reboots and minor hardware changes. If it
  changes, the device derives a new MLS identity and cannot rejoin
  groups as its previous self.

## 6. Comparison Table

| Dimension | Classical (on disk) | HD Shared | HD Device-Bound |
|---|---|---|---|
| **Recovery secret** | nsec backup + vault password + SQLCipher DB | Mnemonic only | Mnemonic + device IDs |
| **Key storage** | vault.db (Argon2id + XChaCha20Poly1305) + SQLCipher | None (re-derived on demand) | None (re-derived on demand) |
| **MLS signing key** | Random Ed25519, one per device | Deterministic Ed25519, same on all devices | Deterministic Ed25519, unique per device |
| **HPKE init keys** | Random X25519, one per KeyPackage | Deterministic X25519, index-based | Deterministic X25519, index-based per device |
| **Device coordination** | None (independent devices) | Required (shared leaf, one committer at a time) | Not required (independent leaves) |
| **Epoch conflicts** | N/A (independent leaves) | Possible if two devices commit concurrently | Not possible (different leaves) |
| **Concurrent commits** | Yes (different leaves) | No (shared leaf) | Yes (different leaves) |
| **Key backup needed** | Yes (vault + DB) | No | No |
| **Compromise scope** | nsec independent from MLS keys | Mnemonic compromises all keys across all protocols | Same as HD Shared |
| **HPKE counter** | Not needed (random keys) | Monotonic counter, recoverable from relay | Per-device counter, recoverable from relay |
| **Use case** | Single device, no mnemonic infrastructure | Multi-device with simple recovery, low-concurrency groups | Multi-device with independent operation |

## 7. The 11 JSON-RPC Methods

The signing-agent API exposes 11 methods over the Unix socket. These
cover all cryptographic operations WhiteNoise needs. The daemon (or
avatar) implements the server side; `sa-client` provides the
client-side trait implementations.

### Nostr identity (secp256k1)

| # | Method | Purpose |
|---|--------|---------|
| 1 | `get_public_keys` | List all Nostr pubkeys managed by this signer |
| 2 | `sign_event` | Schnorr-sign a Nostr event |
| 3 | `nip44_encrypt` | NIP-44 encrypt a plaintext for a peer (ECDH + HKDF + ChaCha20-Poly1305) |
| 4 | `nip44_decrypt` | NIP-44 decrypt a ciphertext from a peer |

### MLS signing (Ed25519)

| # | Method | Purpose |
|---|--------|---------|
| 5 | `get_mls_pubkey` | Return the Ed25519 MLS signing pubkey for a Nostr identity |
| 6 | `mls_sign` | Ed25519-sign arbitrary data (commits, proposals, app messages) |
| 7 | `sign_account_identity_proof` | Schnorr-sign the binding between Nostr npub and MLS leaf |

### HPKE key agreement (X25519)

| # | Method | Purpose |
|---|--------|---------|
| 8 | `mls_hpke_pubkey_at` | Return the X25519 pubkey at a derivation index (`init` or `enc`) |
| 9 | `mls_hpke_dh` | X25519 Diffie-Hellman using a previously issued HPKE key |
| 10 | `mls_next_hpke_init_key` | Advance the init key counter and return the next X25519 pubkey |
| 11 | `mls_hpke_decap` | HPKE decapsulation -- X25519 DH using an init key (Welcome processing) |

### Boot sequence

When `NOSTR_SA_SOCK` is set, WhiteNoise performs:

```
1. connect(NOSTR_SA_SOCK)
2. get_public_keys()                       -> [pk1, pk2, ...]
3. for each pk:
     get_mls_pubkey(pk, null, 0x0001)      -> mls_pk
     register SaMlsSigner(mls_pk)
     register SaHpkeBackend(mls_pk)
4. for each pk:
     login_external_signer(pk, SaAccountClient(pk))
```

### Runtime call mapping

| App operation | Daemon call(s) |
|---|---|
| Send chat message | `mls_sign` |
| Receive commit (UpdatePath) | `mls_hpke_dh` |
| Join group (Welcome) | `mls_hpke_decap` |
| Publish KeyPackage | `mls_hpke_pubkey_at`, `mls_next_hpke_init_key` |
| Relay auth (NIP-44) | `nip44_encrypt`, `nip44_decrypt` |
| Event signing | `sign_event` |
| MLS leaf binding | `sign_account_identity_proof` |

## 8. BIP-32 Path Structure

All keys are derived from a single BIP-39 mnemonic through the
KeyVault's 5-level BIP-32 path. All levels are hardened.

```
m / purpose' / coin_type' / identity'  / algorithm'     / config'
    44         protocol     mangle(id)   alg|var|role     csprng|index
    level 0    level 1      level 2      level 3          level 4
```

### Level encoding

| Level | Name | Bits | Encoding |
|---|---|---|---|
| 0 | purpose | 31 | Fixed: `44` |
| 1 | coin_type | 31 | Protocol enum (see below) |
| 2 | identity | 31 | `mangle(identity_string)` -- SHA-256 truncated to 31 bits |
| 3 | algorithm | 31 | `alg(15) \| variant(8) \| role(8)` |
| 4 | config | 31 | `csprng(7) \| index(24)` |

### Protocol coin types

| Protocol | Coin Type |
|---|---|
| Bitcoin | 0 |
| Nostr | 1237 |
| SSH | 1238 |
| OpenPGP | 1239 |
| X.509 | 1240 |
| WireGuard | 1241 |
| MLS | 1242 |

### Concrete paths

```
Nostr signing (secp256k1 Schnorr):
  m / 44' / 1237' / mangle("alice@atlanta.com")' / SCHNORR|0|0' / 0|0'

MLS signing (Ed25519):
  m / 44' / 1242' / mangle("alice@atlanta.com")' / ED25519|0|SIGN' / 0|0'

MLS HPKE init key #N (X25519):
  m / 44' / 1242' / mangle("alice@atlanta.com")' / ED25519|0|HPKE' / 0|N'
                                                                        ^
                                                         index increments

MLS HPKE init key — device-bound (X25519):
  m / 44' / 1242' / mangle("alice@atlanta.com:cpu_xyz")' / ED25519|0|HPKE' / 0|N'
                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                     device ID mixed into identity hash
```

### AccountIdentityProof

The Nostr key signs a proof binding the npub to the MLS Ed25519
public key. Both keys are derived from the same mnemonic, from
different branches:

```
Nostr branch:  m/44'/1237'/mangle(alice)'/SCHNORR|0|0'/0|0'  -> npub
MLS branch:    m/44'/1242'/mangle(alice)'/ED25519|0|SIGN'/0|0' -> ed25519.pub

proof = BIP-340_Schnorr_Sign(nostr_key,
          SHA-256("marmot.account-identity-proof.v1" || fields))

  "I, npub, authorize ed25519.pub as my MLS signing key"
```

### Algorithm constants

| Constant | Value | Curve | MLS use |
|---|---|---|---|
| `ALG_SCHNORR` | 0 | secp256k1 | Nostr signing only |
| `ALG_ED25519` | 1 | Ed25519 / X25519 | MLS signing and HPKE |

### Role constants (level 3)

| Role | Value | Purpose |
|---|---|---|
| `SIGN` | 0 | MLS signing key (Ed25519) |
| `HPKE` | 1 | HPKE init/enc keys (X25519, derived from Ed25519 seed) |

Ed25519 and X25519 share the same 32-byte seed material. The KeyVault
derives both from the same BIP-32 node using the standard
Ed25519-to-X25519 conversion (SHA-512 hash with clamping). The `role`
byte selects whether the key is used for signing (`SIGN`) or key
agreement (`HPKE`).

The 24-bit index field in level 4 supports up to 16,777,216
KeyPackages per identity.
